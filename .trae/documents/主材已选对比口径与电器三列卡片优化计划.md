# 主材已选对比口径与电器三列卡片优化计划

## Summary

本轮优化聚焦 3 个明确问题：

1. `施工` 与 `定制` 当前虽然展示为双卡片，但没有“左侧已选、右侧对比”的语义，导致顶部汇总把两个商家都计入。新口径已确认：这两个分类里，顶部 `总预算` 和 `总支出` 都只统计左侧已选商家，右侧仅作对比展示。
2. `瓷砖` 区块目前报价明细按纵向一条条堆叠，视觉高度过长，需要改成更紧凑的横向列式布局；同时它始终只有一个商家，不再作为可新增的多商家分类对待。
3. `电器选购` 目前是一张张纵向大卡片堆叠，需要改成“小卡片网格”，桌面端一排展示 3 个。

## Current State Analysis

### 已锁定的实现约束

- 施工、定制顶部汇总都只统计左侧已选商家，右侧对比商家 `预算` 和 `支出` 都排除。
- 瓷砖仍是单商家，不需要新增多商家能力。
- 电器阶段改成网格卡片，但分类与字段保持不变，不引入新业务字段。

## Proposed Changes

### 1. 为主材条目补“已选 / 对比”语义

**文件：**
- 修改：[`src/types/renovation.ts`](file:///Users/bytedance/madiyl.github.io/src/types/renovation.ts)
- 修改：[`src/lib/defaultContent.ts`](file:///Users/bytedance/madiyl.github.io/src/lib/defaultContent.ts)
- 修改：[`src/components/stages/MaterialsStage.tsx`](file:///Users/bytedance/madiyl.github.io/src/components/stages/MaterialsStage.tsx)

**变更内容：**
- 在 `MaterialItem` 上新增可选字段，例如：
  - `quoteRole?: "selected" | "comparison"`
- 该字段只对 `施工`、`定制` 这两个分类有实际业务意义；其他分类可为空。

**为什么要加字段，而不是继续依赖数组顺序：**
- 当前用户描述是“左边已选、右边对比”，这是稳定业务语义，不只是临时排序效果。
- 仅依赖数组顺序会让后续编辑、删除、重排时的汇总口径变得脆弱。

**兼容策略：**
- 在 `mergeWithDefaultContent()` 中为历史数据补兜底：
  - 若分类为 `施工` 或 `定制` 且没有 `quoteRole`
  - 则按当前顺序自动赋值：
    - 第一个条目 -> `selected`
    - 第二个条目 -> `comparison`
    - 超出两个的条目仍标为 `comparison`
- 这样不需要改 Supabase 表结构，只处理 JSON 内容兼容。

### 2. 主材顶部汇总只统计已选商家

**文件：**
- 修改：[`src/components/stages/MaterialsStage.tsx`](file:///Users/bytedance/madiyl.github.io/src/components/stages/MaterialsStage.tsx)

**变更内容：**
- 抽出主材汇总用的派生集合，例如：
  - `summaryMaterials`
- 汇总规则：
  - 对 `施工` / `定制`：
    - 只纳入 `quoteRole === "selected"` 的条目
    - 若历史数据尚未带角色，则使用归一化后的第一项
  - 对其他分类：
    - 保持现状，纳入该分类全部条目
- `BudgetSummary` 的 `budget` / `actualPrice` 都基于这个派生集合求和。

**同时做的显示优化：**
- 在 `施工` / `定制` 卡片顶部增加轻量标签：
  - 左侧已选商家：`已选方案`
  - 右侧对比商家：`对比方案`
- 保持左右顺序固定为：已选在前，对比在后。

### 3. 收紧施工 / 定制的编辑行为

**文件：**
- 修改：[`src/components/stages/MaterialsStage.tsx`](file:///Users/bytedance/madiyl.github.io/src/components/stages/MaterialsStage.tsx)

**变更内容：**
- 对 `施工`、`定制` 分类，在编辑模式下把新增逻辑收紧为“最多 2 张卡片”。
- 当该分类已有 2 个条目时，不再显示 `新增条目`。
- 新增时按缺失角色自动补位：
  - 优先补 `selected`
  - 其次补 `comparison`

**原因：**
- 这是用户已经明确的业务结构：两个商家，其中一个已选、一个对比。
- 不收紧编辑入口，后续仍可能产生第三个条目，汇总口径会重新变模糊。

### 5. 电器阶段改成三列小卡片网格

**文件：**
- 修改：[`src/components/stages/AppliancesStage.tsx`](file:///Users/bytedance/madiyl.github.io/src/components/stages/AppliancesStage.tsx)

**变更内容：**
- 把当前阶段容器从 `space-y-4` 纵向列表改成网格容器，例如：
  - `grid gap-4 md:grid-cols-2 xl:grid-cols-3`
- 每个分类保持“一类一张卡”的信息架构，但压缩成小卡片形态。
- 小卡内部字段改成更适合卡片宽度的布局：
  - 标题固定在卡片顶部
  - 信息区改成更紧凑的 `space-y-*`

**浏览态目标：**

- 平板 2 张。
- 移动端 1 张。

**编辑态目标：**
- 继续允许直接在卡片里编辑，不拆到弹窗或抽屉。
- 如果该分类暂无数据，仍保留当前“新增条目”的入口，但容器也按网格卡片渲染。

## Assumptions & Decisions

1. `施工`、`定制` 的“左侧已选、右侧对比”会落成显式字段，而不是仅靠渲染顺序约定。
2. 顶部汇总对 `施工` / `定制` 的右侧对比方案完全排除，预算和总支出都不计入。
3. 瓷砖“横着列”采用响应式网格子卡方案，而不是继续纵向分隔列表。
4. 瓷砖“仅一个商家，不会新增”在本轮只落实到：
   - 不提供新增入口
   - 单卡片展示优化
   不额外引入新的删除限制或复杂约束。
5. 电器改成三列小卡片时，不改变电器的分类枚举与字段结构，只调整布局与信息层次。

## Verification Steps

1. 主材汇总口径
- 准备 `施工`、`定制` 各两张卡片的数据。
- 确认左侧 `已选方案`、右侧 `对比方案` 标签正确显示。
- 修改右侧对比商家的预算和实际价格，顶部 `总预算 / 总支出` 不应变化。
- 修改左侧已选商家的预算和实际价格，顶部汇总应同步变化。

2. 主材编辑约束
- 在编辑模式下检查：
  - `施工`、`定制` 最多只能有 2 张卡片
  - 角色顺序保持为已选在前、对比在后

3. 瓷砖区块
- 确认 4 个报价项不再纵向拉满整个容器，而是以横向网格分布。
- 在桌面端观察整体高度明显低于旧版。
- 编辑模式下仍能修改每个区域的材料与报价。

4. 电器区块
- 桌面端一排显示 3 张小卡片。
- 平板 2 张，移动端 1 张。
- 每个分类的预算、成交价、状态、备注仍能正常展示和编辑。

5. 静态检查
- 运行 `npm run check`
- 运行 `npm run lint`
- 运行 `npm run build`
